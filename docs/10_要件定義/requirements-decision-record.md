# 工程1 要件決定記録

## 1. 目的

本書は、工程1で確定したExam Trainer v1の要件判断と理由を記録する。詳細な受け入れ条件は[Exam Trainer 要件定義書](exam-trainer-requirements.md)、要件間の対応は[要件トレーサビリティ](../00_開発管理/requirements-traceability.md)を正とする。

## 2. 前提

- 工程0の承認タグ`gate-00-foundation-v1.0`が指す`95ff59caab5dfae16ab587b420004c0a324ab3fb`を工程1の入力とする。
- 承認台帳の工程0「対象コミット」は承認対象成果物の`392736f05b5868d92ca65c74537c6647830a6f6c`であり、タグは承認台帳更新コミットを含む。両者の差は工程0の承認記録だけで、要件の差ではない。
- 本書の決定は工程1の人による承認までは承認候補であり、次工程の正式な入力ではない。

## 3. 決定一覧

| ID | 論点 | 決定 | 理由 |
| --- | --- | --- | --- |
| DR-001 | 選択式の採点 | `single`は選択値が唯一の正解と一致した場合だけ正解とする。`multiple`は選択集合と正解集合が完全一致した場合だけ正解とし、部分点を設けない。順序は採点へ影響させない | 採点を試験非依存かつ再現可能にするため |
| DR-002 | 入力式の正規化 | 回答と各正解候補へUnicode NFC正規化、改行コードのLF統一、文字列の前後のUnicode空白除去を順に適用する。大文字小文字、全角半角、内部空白は変換しない。正規化後にいずれかの正解候補と完全一致した場合だけ正解とする | 意図しない表記同一視を避けながら、入力環境差だけを吸収するため |
| DR-003 | 模擬試験の分野割当 | 正の`weight`が全分野にある場合は最大剰余法で整数枠を割り当て、同率は`domainId`昇順とする。分野不足分は残余の大きい順、同率は`domainId`昇順で空きのある分野へ再配分する。重みがない場合は全問題プールから分野枠なしで抽出する | 同じ入力から割当数を再現でき、問題不足にも対応するため |
| DR-004 | 問題不足 | 試験全体の利用可能な承認済み問題数が指定問題数未満なら開始せず、不足数を表示する。分野だけが不足し全体数を満たせる場合はDR-003で再配分し、開始前に配分差を通知する | 不完全な模擬試験の黙示的な開始を防ぐため |
| DR-005 | 弱点計算 | 1回以上回答した問題を対象に、要件定義11.1の0〜100点の式で優先度を算出し、得点降順、最終回答日時昇順、`questionId`昇順で並べる | 6要素をすべて使い、境界値試験が可能な規則にするため |
| DR-006 | バックアップ競合 | v1の復元は検証とプレビュー後の全置換とし、マージしない。利用者の確認後、単一トランザクションで全対象データを置換し、失敗時は変更前を保持する | 重複・競合解決を利用者へ委ねず、原子的に復元するため |
| DR-007 | 中断再開 | 模擬試験は開始、回答変更、問題移動、見直し変更のたびに保存する。制限時間は保存した絶対期限から算出し、再起動中も経過する。未完了セッションは再開または破棄を選べる | 再起動による時間延長と回答消失を防ぐため |
| DR-008 | 時間切れ | 絶対期限到達時に自動提出する。未回答は不正解として総問題数の分母へ含めるが、回答履歴`attempts`は生成せず、セッション結果に未回答として保持する | 得点の一貫性と「回答した履歴」の意味を両立するため |
| DR-009 | Exam Pack追加 | v1は開発者がリポジトリへPackを配置し、Validator成功後に再ビルドして配布する。利用者による実行時インポートやPack管理UIは対象外とする | 静的PWAと検証済みデータ同梱を維持するため |
| DR-010 | 製品問題数 | OSS-DB Silverは10〜20問の範囲で人が承認した独自問題を同梱する。第2試験デモPackは`single`、`multiple`、`input`を各1問以上、合計3問以上含める | 初期コンテンツの現実的な作成量と汎用性検証を両立するため |
| DR-011 | 試験fixture | 50問と5,000問のfixtureは`tests/fixtures/exam-packs/`だけに置き、製品Packの索引、ビルド成果物、PWAキャッシュへ含めない | 試験データの製品混入を機械的に検証可能にするため |
| DR-012 | 出典と確認日 | 製品へ同梱できる問題は非空の`sources`、`verifiedAt`、`status: approved`を必須とする。下書きは製品Pack外で管理し、これらを省略できる | 下書きの作成容易性と公開品質を分離するため |
| DR-013 | 出典品質 | `sources`は正解と主要な解説を直接確認できる公式資料または一次資料のHTTPS URLを原則とする。一次資料が存在しない場合だけ、理由をレビュー記録へ残して信頼できる二次資料を使用できる | 技術的正確性と追跡可能性を確保するため |
| DR-014 | 問題の独自性 | 実在試験の記憶問題、試験ダンプ、第三者問題集の転記・軽微な言い換えを禁止する。事実だけを参照し、問題文、選択肢、解説を独自に構成する | 権利侵害と試験制度上の不正を避けるため |
| DR-015 | 公開承認 | Validator成功、内容レビューの`承認候補`、人による問題単位または明示した集合単位の承認がそろった問題だけを`approved`にできる。AIは状態を`approved`へ変更しない | 自動判定が人の公開判断を代替しないため |
| DR-016 | バックアップ版 | 現行版と同じ`schemaVersion`は復元できる。既知の旧版は検証済みマイグレーション後に復元し、現行版より新しい版と未知版はデータを変更せず拒否する | 前方非互換によるデータ破損を防ぐため |
| DR-017 | 問題難易度 | 基本事実の再生から複数条件・例外を統合する高度な判断までを5段階で定義する | Pack間で難易度の意味を揃え、レビュー可能にするため |
| DR-018 | 模擬試験設定 | 問題数と制限時間を1以上、Exam Packの設定値以下の整数で指定でき、初期値はPack設定値とする | 少数の製品問題でも短縮模試を実施しつつ、Packの試験設定を上限として維持するため |
| DR-019 | 端末・キーボード対応 | 横幅360px〜1,440pxで主要機能を使え、全操作をキーボードで到達・実行でき、フォーカスを視認できることを必須とする | PC・スマートフォン・キーボード対応を検証可能にするため |
| DR-020 | 製品問題の継続拡充 | OSS-DB Silverの初期同梱数は10〜20問とするが、公開後はValidator、内容レビュー、人の集合または問題単位承認を通過した独自問題を上限なしで追加できる | 初期リリース範囲を維持しつつ、問題プールを継続的に充実させるため |

## 4. 工程2以降へ委ねる事項

次は要件ではなく実現方法であり、工程2または工程3で確定する。

- 最大剰余法、弱点計算、入力正規化を配置するモジュールと公開API
- 乱数生成器、シードの保持方法、問題順のシャッフル方法
- IndexedDBのテーブル、キー、索引、トランザクション境界の具体形
- バックアップJSONとExam PackのZodスキーマの具体形
- 画面レイアウト、文言、色、レスポンシブのブレークポイント
- 既知の旧`schemaVersion`ごとのマイグレーション実装

これらは工程1の決定を変更してはならない。変更が必要な場合は要件変更として台帳へ記録する。
