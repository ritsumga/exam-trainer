# 試験問題妥当性レビュー

Exam Packの問題を、機械検証では判断できない内容品質まで含めてレビューする。このスキルの結果は人の判断材料であり、問題を`approved`または正式公開済みにしない。

## 必要な入力

- 対象の問題Markdown
- 対応する`exam.yaml`と`domains.yaml`
- 問題が参照する資料
- 現工程で承認済みの要件、スキーマ、Validator規則

不足する入力があっても確認可能な範囲はレビューし、確認できない項目を`判定不能`として分離する。

## 手順

1. 最後に承認された工程成果物と現在工程を確認し、未確定の基準を確定事項として扱わない。
2. 対象問題と関連するExam Pack定義を読み、[レビュー基準](references/review-criteria.md)をすべて確認する。
3. 技術的主張を出典と照合する。外部資料の参照が許可されている場合は公式または一次資料を優先し、URLと確認日を残す。
4. 自動Validatorが利用可能なら実行する。利用できない工程では、同等の構造項目を手動確認したことを明示する。
5. 指摘ごとに重要度、根拠、修正案を示し、総合判定案を出す。

## 出力

次の順で簡潔に報告する。

1. 対象問題IDと総合判定案
2. 指摘事項。各項目に`重大`、`中`、`軽微`の重要度、該当箇所、根拠、修正案を含める
3. 確認できた出典と確認日
4. `判定不能`の項目と不足情報
5. 人が最終判断すべき事項

総合判定案は次のいずれかとする。

- `承認候補`: 重大・中の指摘がなく、技術的根拠を確認できた
- `要修正`: 内容または構造に修正すべき問題がある
- `判定不能`: 正確性や権利関係を判断するための根拠が不足している

## 制約

- レビュー結果だけで問題を正式化、公開、または人の承認済みにしない。
- AIまたは自動処理で問題の`status`を`approved`へ変更しない。
- 出典にない説明を事実として補わない。
- 第三者の問題文や解説を転載せず、類似が疑われる場合は人の確認対象にする。
- 製品同梱候補に非空の`sources`または`verifiedAt`がない場合は`要修正`とする。人の承認前レビューでは承認前の`status`を維持して人の最終判断事項へ記載する。公開直前レビューで人の承認記録または`status: approved`がない場合は`要修正`とする。
