# 開発ワークフロー

## 1. ブランチ

工程ごとに次のブランチを使用する。

| 工程 | ブランチ |
| --- | --- |
| 0 | `phase/00-ai-development-foundation` |
| 1 | `phase/01-requirements` |
| 2 | `phase/02-basic-design` |
| 3 | `phase/03-detailed-design` |
| 4 | `phase/04-implementation` |
| 5 | `phase/05-system-test` |
| 6 | `phase/06-release` |

- 新工程のブランチは、直前工程の承認タグが指す`main`から作成する。
- 未承認成果物を`main`へ統合しない。
- 工程4の作業単位は同じ工程ブランチ内で完結させ、工程5を先行させない。

## 2. レビューと承認

Codexは工程末に次を提示する。

- 変更した成果物
- 要件や設計に対する主要判断
- 実行した検証と結果
- 文書とコードコメントの日本語規則への適合結果
- 未解決の課題、リスク、制約
- 承認対象となる完了条件

人の明示的な工程承認だけを承認として扱う。質問への回答、部分的な同意、実装継続依頼は工程承認とみなさない。修正指示がある場合は同じブランチと工程で修正し、再レビューする。

## 3. 承認後のGit操作

承認後、Codexは次の順で処理する。

1. 承認台帳へ承認日、承認者、対象、判定を記録する。
2. 工程成果物と台帳更新をコミットする。
3. `main`へ統合する。
4. `gate-XX-<phase>-v1.0`形式の注釈付きタグを作成する。
5. ローカルの状態とタグを報告する。

工程タグは次を使用する。

| 工程 | タグ |
| --- | --- |
| 0 | `gate-00-foundation-v1.0` |
| 1 | `gate-01-requirements-v1.0` |
| 2 | `gate-02-basic-design-v1.0` |
| 3 | `gate-03-detailed-design-v1.0` |
| 4 | `gate-04-implementation-v1.0` |
| 5 | `gate-05-system-test-v1.0` |
| 6 | `gate-06-release-v1.0` |

push、Pull Request、リポジトリ可視性変更、Pages設定、デプロイ、GitHub Release作成は外部変更である。工程承認とは別に、その操作を実行してよいことを人が明示した場合だけ実行する。

## 4. コミット

- Conventional Commitsに準じ、`docs:`, `feat:`, `fix:`, `test:`, `build:`, `ci:`, `chore:`を使う。
- 1コミットにはレビュー可能な1つの目的だけを含める。
- 生成物とソースを区別し、生成物を手編集しない。
- 承認済み要件へ影響する変更は、コミット本文または工程報告に要件IDを記載する。
- コミットメッセージの作成またはレビューでは、`.agents/skills/commit-message/SKILL.md`を使用する。

## 5. 問題レビュー

問題の追加または変更では、`.agents/skills/question-validity-review/SKILL.md`により公開前レビューを行う。スキルの判定案、Validatorの成功、AIレビューのいずれも人の承認を代替しない。

## 6. 品質ゲート

アプリ基盤作成後の標準コマンドは次とする。各スクリプトは工程4で`package.json`へ定義する。

```powershell
npm ci
npm run validate
npm run lint
npm run typecheck
npm test
npm run build
```

結合・総合試験以降は次も実行する。

```powershell
npm run test:e2e
```

工程0〜3では、少なくとも`git diff --check`、Markdown参照、ID重複、台帳間の状態整合性を確認する。

全工程で、文書の自然文とコードコメントが日本語で記述されていることを確認する。製品名、ライブラリ名、識別子、型名、API名、コマンド、パス、ファイル名、設定値、データ契約、コード例は、技術的に必要な原表記を維持できる。違反がある場合は承認依頼前に修正する。

## 7. GitHub Pages公開

- 公開元は承認済み`main`とし、GitHub Actionsで品質ゲート成功後だけデプロイする。
- Pagesのベースパスは`/exam-trainer/`とする。
- APIキー、アクセストークン、利用者データをビルド成果物へ含めない。
- リポジトリの公開設定変更と初回デプロイは、人の明示承認後に実施する。
- 公開後に直リンク、PWAインストール、更新、オフライン演習、IndexedDB永続化を確認する。

## 8. 差し戻し

- 承認前の差し戻しは工程ブランチ上で修正する。
- 承認後に基準の誤りが判明した場合は、影響をリスク・課題台帳とトレーサビリティへ記録し、変更対象工程へ戻る。
- 承認タグを移動・上書きしない。訂正版はタグ末尾を`v1.1`のように増分する。
