# Exam Trainer 基本アーキテクチャ設計

## 1. 目的

本書は、Exam Trainer v1の主要構成、責務、依存方向、Exam Packの組込み方式、GitHub Pages上の実行方式を定める。型、Zodスキーマ、IndexedDBの索引、関数シグネチャは工程3で確定する。

## 2. 設計方針

| 観点 | 決定 |
| --- | --- |
| 配布方式 | バックエンドを持たない静的PWAとして配布する |
| UI | React、TypeScript、Tailwind CSS、React Routerを使用する |
| ビルド | Viteを使用し、GitHub Pages向けの`base`を`/exam-trainer/`とする |
| 画面URL | GitHub Pagesで直リンクと再読込を成立させるため`createHashRouter`を使用する |
| 問題データ | Git管理するExam Packをビルド時に検証・変換し、製品成果物へ同梱する |
| 学習データ | Dexieを介してIndexedDBへ保存し、問題データとは分離する |
| データ契約 | 外部入力と永続化データの境界をZodで検証する |
| ドメイン処理 | 採点、復習優先度、模擬試験割当、抽出、統計をUIや保存処理から分離する |
| 可変要素 | 現在日時、乱数、永続化、Pack読込を境界として注入可能にする |
| 試験依存 | 共通コードは`examId`、`domainId`、`questionType`などの共通属性だけを扱う |

## 3. システム構成

```text
利用者
  ↓
React UI / Router
  ↓
機能サービス
  ├─ 通常演習
  ├─ 模擬試験
  ├─ 復習
  ├─ 統計
  └─ バックアップ・復元
  ↓
純粋なドメインエンジン
  ├─ 採点
  ├─ セッション生成
  ├─ 復習優先度
  └─ 統計集計
  ↓                    ↓
Exam Pack境界          学習データ境界
  ↓                    ↓
生成済み静的データ      Dexie / IndexedDB
```

依存方向は上位の操作から下位の抽象へ向ける。ドメインエンジンはReact、Dexie、ブラウザAPI、特定Exam Packを参照しない。UIはIndexedDBを直接操作せず、機能サービスとRepository境界を介する。

## 4. レイヤーと責務

| レイヤー | 主な責務 | 禁止事項 |
| --- | --- | --- |
| アプリケーションシェル | ルーター、全体レイアウト、エラー境界、PWA通知 | 採点や試験固有規則を持たない |
| 機能UI | 入力受付、表示状態、アクセシビリティ、機能サービスの呼出し | IndexedDBや生成済みPackファイルを直接操作しない |
| 機能サービス | ユースケースの順序制御、ドメイン処理とRepositoryの調停 | Reactコンポーネントを参照しない |
| ドメインエンジン | 採点、正規化、割当、抽出、復習優先度、統計の純粋計算 | 時刻、乱数、保存、ネットワークを直接参照しない |
| Repository | 学習データの取得・保存・全置換、トランザクション制御 | 問題本文を学習DBへ複製しない |
| Packアダプター | 生成済みカタログと試験単位データの読込 | 未検証の原本Markdownを実行時に解釈しない |
| ビルドツール | Pack原本の検証、正規化、索引生成、製品対象の分離 | 下書き、未承認問題、試験fixtureを製品成果物へ含めない |

## 5. Exam Packのビルド構成

1. `exam-packs/<exam-id>/`だけを製品Pack入力として列挙する。
2. `exam.yaml`、`domains.yaml`、`questions/*.md`を構文・スキーマ・参照整合性・公開条件の順に検証する。
3. Markdown本文とYAML Front Matterを共通モデルへ正規化する。
4. 試験一覧用の軽量カタログと、試験単位の問題データを別々の生成物にする。
5. アプリ起動時はカタログだけを読み、試験選択後に対象Packを読み込む。
6. `tests/fixtures/exam-packs/`は別の入力口とし、製品カタログ、製品ビルド、PWAキャッシュへ接続しない。

生成物のファイル名、分割単位、生成先、コミット有無は工程3で確定する。実行時に利用者がPackを追加、更新、削除する経路は設けない。

## 6. ドメインエンジン

### 6.1 採点

`single`、`multiple`、`input`を判別共用体として受け取り、すべての回答値を文字列配列として扱う。採点は正誤と表示用の正規化結果を返し、履歴保存や画面表示を行わない。

### 6.2 通常演習生成

未回答、誤答、お気に入り、分野別、ランダム、弱点の条件から候補IDを作り、重複なしで指定数を選ぶ。履歴とお気に入りの取得は機能サービス、候補の絞込みと順序決定は純粋関数が担当する。

### 6.3 模擬試験生成

全分野に正の重みがある場合は最大剰余法を使い、それ以外は全体プールから抽出する。問題不足判定、分野不足の再配分、配分差、選択された問題ID列を返し、保存や画面遷移を行わない。抽出と順序決定には`RandomSource`を渡す。

### 6.4 復習優先度と統計

復習優先度は回答履歴、現在日時、現行Packの問題ID集合を入力とし、丸め前得点を含む並び順を返す。統計は履歴と完了セッションから集計結果を生成し、グラフ描画はRechartsを使用するUI側の責務とする。

## 7. 公開境界

| 境界 | 基本責務 | 依存元 |
| --- | --- | --- |
| `ExamPackCatalog` | 試験一覧の取得、`examId`による検証済みPack読込 | 機能サービス |
| `LearningRepository` | 回答、ブックマーク、復習状態、模試セッション、設定の取得・保存 | 機能サービス |
| `BackupRepository` | 全バックアップ対象の読取、単一トランザクションによる全置換 | バックアップ機能サービス |
| `RandomSource` | 再現可能な乱数列の供給 | 演習・模試生成エンジン |
| `Clock` | 現在日時の供給 | 復習、期限判定、保存処理 |
| `AIProvider` | 将来の問題生成候補とレビュー結果の作成 | v1では依存元なし |

境界のTypeScriptシグネチャ、エラー型、非同期方式は工程3で確定する。`RandomSource`のシードは模擬試験セッションに保持して再現可能にし、具体的な生成器とシャッフル方式は工程3で固定する。

## 8. ルーティングと配布

- 公開先は`https://<owner>.github.io/exam-trainer/`を想定する。
- Viteのアセット基準パスを`/exam-trainer/`に固定する。
- アプリ内画面はURLのhash部分へ置き、静的ホストへ画面パスを要求しない。
- 不明な試験、問題、セッション、経路は共通の「見つからない」画面へ遷移し、試験選択へ戻れるようにする。
- GitHub ActionsによるビルドとPages公開は工程4および工程6の対象とし、工程2では実行しない。

## 9. 非機能設計

- 試験カタログと試験データを分離し、起動時に全問題を読み込まない。
- 選択済みPackは`questionId`と`domainId`から参照しやすい実行時索引を構築する。
- 一覧・統計画面では必要な集計結果だけを状態へ保持し、Reactの描画ごとに全履歴を再集計しない。
- ドメインエンジンを純粋関数とし、5,000問fixtureを使った独立性能試験を可能にする。
- バックエンド、認証、クラウドDB、課金APIを依存に加えない。
